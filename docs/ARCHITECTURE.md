# Flipper: architecture

How the game is built. Agents keep this document in sync with the code; the design (what to build) lives in `docs/GAME_DESIGN.md`.

## Overview

```
 pointer / touch / keyboard
            │
            ▼
 src/game (Phaser scenes) ── step(), and later throw(…) etc. ──►  src/core (Simulation: rules + planck physics)
            ▲                                                              │
            └────────────────────── snapshot() every frame ◄──────────────┘

 src/debug/testHooks.ts exposes the same Simulation to tests as window.__FLIPPER__
 src/debug/tuningPanel.ts (dev builds and ?debug) edits the tuning of the running Simulation
```

- **src/core** owns the game state and rules. It is plain TypeScript that runs anywhere, including Node for unit tests, and it is deterministic: the same seed and the same inputs always produce the same result.
- **src/game** is the Phaser layer. Scenes step the simulation on a fixed clock, draw its latest snapshot, play effects, and translate input into simulation calls.
- **Test hooks** (`window.__FLIPPER__`, dev builds and `?testhooks`) let e2e tests and `npm run snap` read the exact state and step the simulation frame by frame, because a canvas game can't be tested through the DOM.

## Game loop

Phaser calls `GameScene.update(time, delta)` once per display frame. The scene feeds `delta` to a fixed-step accumulator (`src/core/fixedStep.ts`), which calls `Simulation.step()` in exact 1/60 s steps: at most 5 per frame, with any longer backlog dropped (for example after the tab was hidden). The scene then draws the newest snapshot. Physics results therefore don't depend on the display's frame rate, and tests can step the simulation directly.

## Coordinates and units

| Quantity | Convention |
| --- | --- |
| Position | meters; origin at the top-left; x to the right, y down |
| Angle | radians; positive is clockwise (same as Phaser's rotation); 0 is upright |
| Time | seconds; fixed step `SIM_DT` = 1/60 s |
| Screen | 1280×720 px logical canvas (landscape, for desktop browsers), scaled with `Scale.FIT`; 1 m = 100 px, so the visible world is 12.8 m × 7.2 m |
| Table | top surface `TABLE_TOP_Y` = 5.6 m (78% of the way down); ends `TABLE_LEFT_X` = 1.6 m and `TABLE_RIGHT_X` = 11.2 m, so 1.6 m of screen on each side; all in `src/core/table.ts` |
| Bottle | its body origin (the snapshot's `x`, `y`) is the center of the flat base; its shape extends toward negative y, so the cap is at y = −`BOTTLE_HEIGHT` in local coordinates. Held at the hand, `HAND_X` = 2.8 m, `HAND_Y` = 4.6 m (base 1 m above the table top, 1.2 m in from the left end); both in `src/core/bottle.ts` |

## Testing strategy

| Layer | Tool | What it proves |
| --- | --- | --- |
| `src/core` | Vitest unit tests | rules and physics outcomes, determinism |
| Layering | `tests/unit/architecture.test.ts` | core stays pure; the game layer never imports planck |
| The game in a browser | Playwright e2e tests via `window.__FLIPPER__` | scenes, input, game flow, no console errors |
| Visuals | `npm run snap`, plus an agent looking at the screenshots | layout, readability, nothing off screen |
| Harness | `tests/harness/` | plan validation, next-action choice, guard rails |

`npm run verify` runs all of it, and the harness runs it again after every builder and maintainer session.

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| D1 | Browser game in TypeScript with Phaser 3.90 and Vite | Runs on desktop and mobile browsers with no install. Everything is text, so agents can build, test and screenshot it headlessly. Phaser 3 is the version agents know best; Phaser 4 is a possible later upgrade. |
| D2 | planck.js (Box2D) for physics instead of Phaser's bundled Matter.js | Stable resting contacts and sleep detection (needed to judge a landing), continuous collision for a fast-spinning bottle, joints if the water gets simulated, and it runs headless in Node for unit tests. |
| D3 | All rules in a deterministic, fixed-step `src/core` | Tests can reproduce any situation exactly (seed plus inputs), and agents can verify gameplay without a browser. |
| D4 | `window.__FLIPPER__` test hooks | A canvas can't be inspected through the DOM; the hooks give tests exact state and frame-by-frame control. |
| D5 | Landscape 1280×720 logical canvas | The game targets desktop browsers, which are landscape; the table is wide and a toss stays comfortably on screen. `Scale.FIT` letterboxes other window shapes. The design allows changing the orientation later: only `GAME_WIDTH`/`GAME_HEIGHT` and the table constants would move. |
| D6 | Placeholder art drawn in code | No asset pipeline until the art direction is decided. |
| D7 | The held bottle is a kinematic body; `Bottle.release()` makes it dynamic | It can't drift or sleep while it waits, and a throw only has to call `release()` and apply an impulse. A kinematic body reports zero mass, so use `bottleMassProperties` for mass before a release. |
| D8 | The water is one more fixture on the bottle body with density, `isSensor` and a zero collision mask | It adds mass and moves the center of mass but never collides, so no contact events come from it. `setWater` rebuilds it. |
| D9 | `setTuning` and `setWater` only touch the bottle while the phase is `aiming` | A bottle in flight keeps the body and launch it was given, so retuning (the tuning panel) or changing the water mid-throw can never alter a flight or make `lastThrow.water` disagree with the bottle. Tuning for later throws and bottles still updates. |
| D10 | A throw is two impulses at the center of mass, `p/100` of the tuning's linear and angular impulse at power 100, and the body divides them by its own mass and inertia | This is decision P2 in code: the water's mass and inertia lower the speed and spin without special cases. The linear impulse is linear in power; the angular impulse follows the spin curve (D23). |
| D11 | The landing is judged by a `LandingJudge` that only reads samples (pose, speeds, table contact) once per step, created at release with the tuning of that moment | Decision P4 in code: nothing can move or turn the bottle to help or hurt a landing, and retuning mid-flight can't change how a flight is judged (as D9). Everything counts steps (P5); the thresholds are all `Tuning` fields. |
| D12 | Resting means nearly still **and touching the table**: a success needs 0.5 s (30 steps, `uprightHoldSeconds`) upright (within 15° modulo a full turn) and at least one turn (D22; upright with 0 turns is the fail `noFlip`, decided at the same step), a fail 0.5 s still and not upright (more than 135° off is `cap`, else `side`). `offTable` is the lowest point 0.1 m below the tabletop, `offScreen` is the whole bottle past the left, right or bottom edge, `timeout` is 300 steps after release. Priority within a step: offScreen, offTable, upright, side/cap, timeout | Contact keeps the slow top of a flight from counting as rest; the success hold was 1 s until F030 shortened it to 0.5 s, the same as the fail wait: a bottle that is within 15° and nearly still cannot fall any more (it would have to tip about 55° to go over), so the second half of the old hold was only waiting, and neither a win nor a loss makes the player wait more than half a second. A success that completes on the timeout step wins. Changing the hold changes when a success is declared, not whether it happens: `scripts/flip-windows.ts` gives the same windows as at 1 s. |
| D13 | The step that sets the outcome also sets the phase to `result`, adds the outcome's `points` to `score`, and starts the delay; `snapshot().outcome` is fixed for that throw and kept through `result`, and the next bottle starts with `null` | The judge decides once; the phase, the score and the HUD (F007) all follow from that one step. Physics keeps running during `result`, so the judged bottle can still settle in view. |
| D14 | `placeBottle(pose)` is the only way to start a throw from an exact state, works only while `aiming`, and leaves `lastThrow` null. `pose.turns` (optional, any finite number, 0 by default) is credited to the judge as rotation already made | Tests and snaps create landings directly (water level from `setWater` first). It isn't a throw with a power, so it has no `lastThrow`, but it counts in `throws` like any other release. A bottle placed upright has made no turn, so without the credit it would be a "no flip" (D22); the credit lets a test script a success of 1, 2 or 3 turns while only adding to `rotation`: it moves nothing. |
| D15 | After the result delay (60 steps, 1 s, `resultDelaySeconds`, counted from the outcome step; it was 90 steps until F030) or `skip()`, the judged bottle's body is destroyed and a new `Bottle` is created in the hand with `drawWaterLevel(rng, tuning)` (the seed's next value), using the tuning in effect then. The result's length (delay plus replay, at the replay speed then) is computed once when the outcome is set (F036), so `setTuning` during a result never shortens or lengthens it | A fresh body is upright, still and unaffected by gravity with no leftover contacts or sleep state, and the next bottle's water is a pure function of the seed and how many bottles came before. Skipping the wait never changes the water sequence or any later throw. `skip()` does nothing outside `result`. |
| D16 | `throws` counts a throw when the bottle is released (by `throwBottle` or `placeBottle`); `score` adds the outcome's points when it is decided. `lastThrow` keeps describing the last real throw while the next bottle waits | "Throws made so far" includes the one in the air. The HUD's throw number is the snapshot's `throwNumber` (D26), because `throws` never goes back (the tuning panel's last-throw readout tells decided throws apart by it). |
| D17 | The power bar is a `PowerMeter` owned by the Simulation, stepped in `Simulation.step()` in every phase, and it is the one place that adds, removes or clamps power. It starts at `powerStart` (50) and nothing but the player's input (or `setPower`) changes it: a throw, a result and the next bottle all leave it alone | The bar is the player's own setting, so it belongs to the player, not the bottle; adjusting during a result lets them set up the next throw. Counting the hold in fixed steps (P5) makes a hold the same at any frame rate and lets tests hold a key for exactly 60 steps. |
| D18 | `Simulation.throwOrSkip()` decides what Space does by phase, and the scene calls it only for a key's first keydown (`event.repeat` is false). `PowerMeter.press` also ignores a key that is already held | Holding Space through a result must not throw the next bottle by itself, and the scene must stay a thin forwarder with the rules in core. A left press tries `sim.mouse.grab` first and `skip()` after it (D25); each only works in its own phase, so a press does at most one of them. |
| D19 | The result flash fades by `snapshot().resultSteps` (steps since the outcome, counted by the Simulation for the result delay anyway), not by wall-clock time or by when the scene first noticed the outcome. The result message is a `Text` that is hidden (not just emptied) when there is no outcome. UI text is tested through `window.__FLIPPER__.texts()`, which returns only shown text | The look of any frame is a function of the snapshot, so a paused game stepped by a test or a snap shows exactly the same flash every time, and a frame that sees the outcome late still draws the right fade. Hiding the message rather than emptying it keeps tests honest about what the player sees. The scene redraws once per frame: after stepping from a test, wait a frame (`visibleTexts(page)` in `tests/e2e/helpers.ts`) before reading `texts()`. |
| D20 | A flip window is a run of neighboring sweep results that are successes with the same `turns` (the outcome's rotation in whole turns); its `width` is `high - low`, so a window of one power has width 0. A sweep runs the real `Simulation` with the water set by `setWater` and stops at the step that starts `result`; calibration, the tuning panel and the benchmark read the game only through it | Calibration must measure what the player gets, so there is no second model of the throw. Turns come from the judge's own `rotation`, so they follow the physics. `high - low` is the measured span; the true edge lies up to one power step beyond each end. |
| D21 | A mouse push is measured by `pushPower` as the pointer's path through its samples (straight lines between samples closer than one 60 Hz frame; over a longer gap the pointer stays put and moves during the last frame before the next sample), cut to the last 150 ms before the newest sample. Distance is the net upward travel over the window; speed is the fastest upward travel over any 50 ms inside it (not the window average); both are fractions of a full-power value (300 px, 2000 px/s) and the weights are equal. The caller adds a sample at the release time, and positions are in logical game pixels. The rule is unchanged since F011, but since F033 the samples it gets are the mouse's own (125 Hz or more), not one per frame (D25) | Reading the path rather than the samples makes 60 Hz and 1000 Hz give the same power (under 0.4 points on the test motions). It cannot make 30 Hz give the same: a browser sends one `pointermove` per frame, so with slow frames the samples are far apart and a gap over one 60 Hz frame reads as "sat still, then moved in the last 1/60 s" (right for a pause, wrong for a pointer that kept moving). A steady 200 px push over 150 ms read 66.7 at 60 Hz or 1000 Hz and 77.8 at 30 Hz, and one 50 ms frame hitch inside a push at 60 fps added about 16 points. The bridge rule stays as it is, because it is right for a real pause and every `push.test.ts` case depends on it; the fix is to give it the samples the browser hides between frames (D25), which leaves the rule and its tests as they were. Speed as a peak over 50 ms rewards a push that is quick and then stops, and never divides by a tiny time, so the first jittery event of a drag can't spike. Holding still through a pause, as a mouse reports only when it moves, keeps a flick after a pause from being smeared over the pause. Logical pixels keep the window size out of the power. 40 px in 150 ms gives about 13 and 300 px gives 100, so an ordinary mouse reaches the whole range. |
| D22 | A landing needs at least one full turn, and an upright landing scores its turns. The judge keeps its upright rule as it was and, when it would call a bottle upright, checks `turns` (the rotation rounded to whole turns, either direction): 0 turns gives the fail `noFlip` and 0 points, otherwise a success with `points = \|turns\|` (`pointsForTurns`). A bottle that turned 0.9 of a turn and tipped back counts, since its turns round to 1. The message wording ("Nailed it! +1", "Double! +2", "Triple! +3", "Flip ×N! +N", "No flip!", "Down!") lives in `src/game/view/resultStyle.ts`, chosen from `outcome.points` and `reason`. `score` adds `outcome.points`. The rule is a judgment on the count, never a push: nothing rotates or snaps the bottle | The design (2026-11-16) makes a plain drop at power 0 a fail and rewards more turns, so the count is a rule of the judge and the same number is both the rule and the points. | D34 | The small effects (camera shake, particle burst, message pop-in) are pure functions of simulation ticks, and the scene only draws them. The shake is not Phaser's `camera.shake` (real time, `Math.random`): `Effects` computes the camera's offset for the snapshot's tick and the scene sets the camera's scroll to it, so a test or snap that steps a paused simulation sees an exact frame, the effect holds still while the game is paused, and the same events always give the same picture. A harder impact never shakes less than a softer one, and a stronger shake in progress is not cut short by a softer impact; an impact under `shakeMinSpeed` (a bottle at rest, or the taps of one settling) makes none, as it makes no sound. | D35 | Sloshing water is pinned to the base in the air and becomes the sliding body only as the bottle comes down to the table (F025). | With the water as a second body on a joint for the whole flight, planck's solver leaked angular momentum: two bodies turning up to a radian per step, held together by a joint, lost about 40% of their spin in five steps at power 80 (with every damping at 0 and the water never leaving the base; more iterations did not help, and 16 substeps per step still lost 20% in 40 steps). Pinning is exact physics for this model, not a shortcut: the water's center is nearer the base than the bottle's center of mass at every level (so the spin presses it down) and in free fall gravity moves shell and water alike, so only the table can move it, and with the joint the whole flight the water stayed on the base until the first table contact too, apart from a solver transient of up to about 1 cm in the first two steps of a throw at power 80 to 100 (found by an outside review). Pinned, the flight is identical to solid water's (unit-tested step by step) and the release comes before the first table contact at every level and power, also with no damping at all (an outside review found that the first trigger, which only followed the center's fall, let a fast-spinning corner touch first in 337 of 1,717 no-damping throws; the default tuning was never affected, and the fix left its windows and rates unchanged). ### Core state

```ts
type Phase = 'aiming' | 'flying' | 'result' | 'roundOver';
interface SimSnapshot {
  tick: number; seed: number; phase: Phase; power: number; // the bar, 0–100 (live push while dragging)
  dragging: boolean; // a mouse or a finger holds the bottle
  bottle: BodySnapshot & { water: number; waterOffset?: number }; // water: filled fraction 0–1
  lastThrow: { power: number; water: number; source: 'keyboard' | 'mouse' | 'touch' } | null; // touch from F037
  outcome: { result: 'success' | 'fail'; reason: 'upright' | 'noFlip' | 'side' | 'cap' | 'offTable' | 'offScreen' | 'timeout';
             rotation: number; turns: number; points: number } | null; // points: turns for a success, 0 for a fail
  resultSteps: number | null; // steps since the outcome; null outside the result phase
  score: number; throws: number; throwNumber: number; throwsPerRound: number; landings: number; streak: number;
}
```

Flow: `aiming` → throw → `flying` → outcome → `result` → delay or `skip()` → `aiming`, or `roundOver` after throw 10. The simulation also queues events (`throw`, `impact` with speed, `outcome`) that the scene drains each frame for sound and effects.

### Key decisions

| # | Decision | Why |
| --- | --- | --- |
| P1 | Power is one number, 0–100; `throwBottle(power, source)` is the only way to throw | the design makes both inputs identical to the physics |
| P2 | The throw is an impulse that mass and inertia divide | heavier bottles get less speed and spin without special cases |
| P3 | Water is mass filling the bottle from the base to its level, solid until M6 | the drawn level and the physics agree |
| P4 | Outcomes are judged from physics state; nothing moves the bottle after release | the design says physics decides |
| P5 | Delays, hold times, timeouts and replay length count fixed steps in core | deterministic, and tests drive them with `step()` |
| P6 | Tuning is a plain object the Simulation accepts as overrides | the tuning panel and tests change the feel without code edits |
| P7 | Flip windows are measured by headless power sweeps and locked by unit tests | calibration can't silently regress |
| P8 | Screens and game pause live in `src/game`; pausing just stops stepping | core has no clock to pause |
| P9 | Sound and effects react to simulation events | core stays free of audio and Phaser |
| P10 | Saves use one versioned localStorage key; the rules (`updateBest`) live in core | storage is a browser API; the rules stay testable |
| P11 | Sloshing is a second body on a prismatic joint along the bottle's axis, created as the bottle nears the table (pinned in the air, D35) | the simplest moving mass that changes the landing, without the joint's spin leak in flight |
| P12 | Phones use the same 1280×720 canvas, rules and tuning; only the input path and page behavior adapt, and a finger push goes through the mouse's grab with its own tuning | one game for both; the push stays one rule in core |
| P13 | Phone tests are a second Playwright project (740×360, touch) over `tests/e2e/phone/` only | the desktop suite isn't run twice, and 740×360 draws the canvas at exactly half size |
| P14 | "Touch device" means no fine pointer (`(any-pointer: fine)` false); it picks the hints, the portrait message and fullscreen | a touchscreen laptop keeps the desktop behavior |
