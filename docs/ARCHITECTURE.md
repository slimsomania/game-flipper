# Flipper: architecture

How the game is built. Agents keep this document in sync with the code; the design (what to build) lives in `docs/GAME_DESIGN.md`.

## Overview

```
 pointer / touch / keyboard
            │
            ▼
 src/game (Phaser scenes) ── step(), and later throw(…) etc. ──►  src/core (Simulation: rules + planck physics)
            ▲                                                              │
            └────────────────────── snapshot() every frame ◄──────────────┘

 src/debug/testHooks.ts exposes the same Simulation to tests as window.__FLIPPER__
 src/debug/tuningPanel.ts (dev builds and ?debug) edits the tuning of the running Simulation
```

- **src/core** owns the game state and rules. It is plain TypeScript that runs anywhere, including Node for unit tests, and it is deterministic: the same seed and the same inputs always produce the same result.
- **src/game** is the Phaser layer. Scenes step the simulation on a fixed clock, draw its latest snapshot, play effects, and translate input into simulation calls.
- **Test hooks** (`window.__FLIPPER__`, dev builds and `?testhooks`) let e2e tests and `npm run snap` read the exact state and step the simulation frame by frame, because a canvas game can't be tested through the DOM.

## Game loop

Phaser calls `GameScene.update(time, delta)` once per display frame. The scene feeds `delta` to a fixed-step accumulator (`src/core/fixedStep.ts`), which calls `Simulation.step()` in exact 1/60 s steps: at most 5 per frame, with any longer backlog dropped (for example after the tab was hidden). The scene then draws the newest snapshot. Physics results therefore don't depend on the display's frame rate, and tests can step the simulation directly.

## Coordinates and units

| Quantity | Convention |
| --- | --- |
| Position | meters; origin at the top-left; x to the right, y down |
| Angle | radians; positive is clockwise (same as Phaser's rotation); 0 is upright |
| Time | seconds; fixed step `SIM_DT` = 1/60 s |
| Screen | 1280×720 px logical canvas (landscape, for desktop browsers), scaled with `Scale.FIT`; 1 m = 100 px, so the visible world is 12.8 m × 7.2 m |
| Table | top surface `TABLE_TOP_Y` = 5.6 m (78% of the way down); ends `TABLE_LEFT_X` = 1.6 m and `TABLE_RIGHT_X` = 11.2 m, so 1.6 m of screen on each side; all in `src/core/table.ts` |
| Bottle | its body origin (the snapshot's `x`, `y`) is the center of the flat base; its shape extends toward negative y, so the cap is at y = −`BOTTLE_HEIGHT` in local coordinates. Held at the hand, `HAND_X` = 2.8 m, `HAND_Y` = 4.6 m (base 1 m above the table top, 1.2 m in from the left end); both in `src/core/bottle.ts` |

## Testing strategy

| Layer | Tool | What it proves |
| --- | --- | --- |
| `src/core` | Vitest unit tests | rules and physics outcomes, determinism |
| Layering | `tests/unit/architecture.test.ts` | core stays pure; the game layer never imports planck |
| The game in a browser | Playwright e2e tests via `window.__FLIPPER__` | scenes, input, game flow, no console errors |
| Visuals | `npm run snap`, plus an agent looking at the screenshots | layout, readability, nothing off screen |
| Harness | `tests/harness/` | plan validation, next-action choice, guard rails |

`npm run verify` runs all of it, and the harness runs it again after every builder and maintainer session.

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| D1 | Browser game in TypeScript with Phaser 3.90 and Vite | Runs on desktop and mobile browsers with no install. Everything is text, so agents can build, test and screenshot it headlessly. Phaser 3 is the version agents know best; Phaser 4 is a possible later upgrade. |
| D2 | planck.js (Box2D) for physics instead of Phaser's bundled Matter.js | Stable resting contacts and sleep detection (needed to judge a landing), continuous collision for a fast-spinning bottle, joints if the water gets simulated, and it runs headless in Node for unit tests. |
| D3 | All rules in a deterministic, fixed-step `src/core` | Tests can reproduce any situation exactly (seed plus inputs), and agents can verify gameplay without a browser. |
| D4 | `window.__FLIPPER__` test hooks | A canvas can't be inspected through the DOM; the hooks give tests exact state and frame-by-frame control. |
| D5 | Landscape 1280×720 logical canvas | The game targets desktop browsers, which are landscape; the table is wide and a toss stays comfortably on screen. `Scale.FIT` letterboxes other window shapes. The design allows changing the orientation later: only `GAME_WIDTH`/`GAME_HEIGHT` and the table constants would move. |

| D11 | The landing is judged by a `LandingJudge` that only reads samples (pose, speeds, table contact) once per step, created at release with the tuning of that moment | Decision P4 in code: nothing can move or turn the bottle to help or hurt a landing, and retuning mid-flight can't change how a flight is judged (as D9). | D12 | Resting means nearly still **and touching the table**: a success needs 1 s upright (within 15° modulo a full turn) and at least one turn (D22; upright with 0 turns is the fail `noFlip`, decided at the same step), a fail 0.5 s still and not upright (more than 135° off is `cap`, else `side`). `offTable` is the lowest point 0.1 m below the tabletop, `offScreen` is the whole bottle past the left, right or bottom edge, `timeout` is 300 steps after release. Priority within a step: offScreen, offTable, upright, side/cap, timeout | Contact keeps the slow top of a flight from counting as rest; the fail wait is shorter than the success hold so a lost bottle doesn't make the player wait a second. A success that completes on the timeout step wins. |
| D13 | The step that sets the outcome also sets the phase to `result`, adds the outcome's `points` to `score`, and starts the delay; `snapshot().outcome` is fixed for that throw and kept through `result`, and the next bottle starts with `null` | The judge decides once; the phase, the score and the HUD (F007) all follow from that one step. Physics keeps running during `result`, so the judged bottle can still settle in view. |
| D14 | `placeBottle(pose)` is the only way to start a throw from an exact state, works only while `aiming`, and leaves `lastThrow` null. `pose.turns` (optional, any finite number, 0 by default) is credited to the judge as rotation already made | Tests and snaps create landings directly (water level from `setWater` first). A bottle placed upright has made no turn, so without the credit it would be a "no flip" (D22); the credit lets a test script a success of 1, 2 or 3 turns while only adding to `rotation`: it moves nothing. |
| D15 | After the result delay (90 steps, `resultDelaySeconds`, counted from the outcome step) or `skip()`, the judged bottle's body is destroyed and a new `Bottle` is created in the hand with `drawWaterLevel(rng, tuning)` (the seed's next value), using the tuning in effect then | A fresh body is upright, still and unaffected by gravity with no leftover contacts or sleep state, and the next bottle's water is a pure function of the seed and how many bottles came before. Skipping the wait never changes the water sequence or any later throw. `skip()` does nothing outside `result`. |
| D16 | `throws` counts a throw when the bottle is released (by `throwBottle` or `placeBottle`); `score` adds the outcome's points when it is decided. `lastThrow` keeps describing the last real throw while the next bottle waits | "Throws made so far" includes the one in the air. | D17 | The power bar is a `PowerMeter` owned by the Simulation, stepped in `Simulation.step()` in every phase, and it is the one place that adds, removes or clamps power. | D18 | `Simulation.throwOrSkip()` decides what Space does by phase, and the scene calls it only for a key's first keydown (`event.repeat` is false). `PowerMeter.press` also ignores a key that is already held | Holding Space through a result must not throw the next bottle by itself, and the scene must stay a thin forwarder with the rules in core. | D19 | The result flash fades by `snapshot().resultSteps` (steps since the outcome, counted by the Simulation for the result delay anyway), not by wall-clock time or by when the scene first noticed the outcome. The result message is a `Text` that is hidden (not just emptied) when there is no outcome. UI text is tested through `window.__FLIPPER__.texts()`, which returns only shown text | The look of any frame is a function of the snapshot, so a paused game stepped by a test or a snap shows exactly the same flash every time, and a frame that sees the outcome late still draws the right fade. The scene redraws once per frame: after stepping from a test, wait a frame (`visibleTexts(page)` in `tests/e2e/helpers.ts`) before reading `texts()`. |
| D20 | A flip window is a run of neighboring sweep results that are successes with the same `turns` (the outcome's rotation in whole turns); its `width` is `high - low`, so a window of one power has width 0. A sweep runs the real `Simulation` with the water set by `setWater` and stops at the step that starts `result`; calibration, the tuning panel and the benchmark read the game only through it | Calibration must measure what the player gets, so there is no second model of the throw. Turns come from the judge's own `rotation`, so they follow the physics. `high - low` is the measured span; the true edge lies up to one power step beyond each end. |
| D21 | A mouse push is measured by `pushPower` as the pointer's path through its samples (straight lines between samples closer than one 60 Hz frame; over a longer gap the pointer stays put and moves during the last frame before the next sample), cut to the last 150 ms before the newest sample. Distance is the net upward travel over the window; speed is the fastest upward travel over any 50 ms inside it (not the window average); both are fractions of a full-power value (300 px, 2000 px/s) and the weights are equal. The caller adds a sample at the release time, and positions are in logical game pixels | Reading the path rather than the samples makes 60 Hz and 1000 Hz give the same power (under 0.4 points on the test motions). Speed as a peak over 50 ms rewards a push that is quick and then stops, and never divides by a tiny time, so the first jittery event of a drag can't spike. Holding still through a pause, as a mouse reports only when it moves, keeps a flick after a pause from being smeared over the pause. Logical pixels keep the window size out of the power. 40 px in 150 ms gives about 13 and 300 px gives 100, so an ordinary mouse reaches the whole range. |
| D22 | A landing needs at least one full turn, and an upright landing scores its turns. The judge keeps its upright rule as it was and, when it would call a bottle upright, checks `turns` (the rotation rounded to whole turns, either direction): 0 turns gives the fail `noFlip` and 0 points, otherwise a success with `points = \|turns\|` (`pointsForTurns`). A bottle that turned 0.9 of a turn and tipped back counts, since its turns round to 1. The message wording ("Nailed it! +1", "Double! +2", "Triple! +3", "Flip ×N! +N", "No flip!", "Down!") lives in `src/game/view/resultStyle.ts`, chosen from `outcome.points` and `reason`. `score` adds `outcome.points`. The rule is a judgment on the count, never a push: nothing rotates or snaps the bottle | The design (2026-11-16) makes a plain drop at power 0 a fail and rewards more turns, so the count is a rule of the judge and the same number is both the rule and the points. Deciding `noFlip` at the same step as a success keeps the result timing identical, and the physics still decides whether the bottle stands. Keeping the words in the view and the number in the core means a test can read `points` without parsing text. |
| D23 | The default throw is calibrated with six levers and no rule: a squat bottle (1.0 m wide, 1.13 m tall, see `bottleShape.ts`), a heavy shell (`shellDensity`), high friction and little bounce, strong `bottleAngularDamping`, a little `bottleLinearDamping`, and a spin curve `spinFraction(p) = (p/100)^exponent · exp(growth·(p−100))` (exponent 0.03, growth 0.013, so the spin is nearly `exp(growth·p)`) in front of the angular impulse. `tests/unit/calibration.test.ts` locks the design's targets (window widths, the 1.5 to 2 times rise, doubles above singles), not these numbers | Measured, not guessed: a landing is upright over only about 0.25 to 0.3 of a turn of landing angle, so a window of 12 or more powers needs the rotation to change by at most about 0.02 turns per power point. Strong spin damping makes the rotation settle early in the flight (rotation is about the launch spin divided by the damping, independent of the flight time), the squat shape and sticky landing widen the angle the bottle tips back from, and the exponential spin curve keeps the relative rise of the rotation about the same (about 1.3 % per power point) from the light bottle's window to the full bottle's, so every window is about 12 to 16 points wide and a double flip lies about 40 points above a single instead of 1.4 times higher. With a linear spin, hill-climbing over every other lever (shape, density, friction, bounce, damping, impulses, angle) never got the 10% bottle's window past 9 or 10 points while the 90% bottle still had a double flip by power 100 (a window of 12 points at power 30 to 40 needs a bottle that lands upright over about 0.4 turns, and the best shape gave 0.27). Retune with `sweepPowers`/`findWindows` (`npx tsx scripts/flip-windows.ts` prints the table), not by hand. |
| D24 | The developer tuning panel is plain DOM over the canvas, and everything it changes goes through one `TuningControl` that calls `Simulation.setTuning` and `Simulation.lockWater`; the test hooks `tuning()`, `setTuningValue()` and `lockWater()` call the same control. It is on in dev builds and with `?debug` only (`?testhooks` alone gives the hooks but no panel and no saved edits). Only the values that differ from `DEFAULT_TUNING` are saved (key `flipper.debug.tuning`, with the water lock), and a new `GameScene` simulation starts with them. Key events inside the panel stop there (`stopPropagation`), and Backquote is bound on the window in the capture phase | A second path to the simulation would let the panel, the hooks and a restart disagree, so there is one. A game that hears the panel would move the power bar, throw or restart while the developer types a number; Phaser listens on the window, so stopping the event at the panel is enough, and the capture-phase Backquote still closes the panel from inside a field. Saving only differences means that after the human pastes the Copy JSON into `tuning.ts` the saved values equal the defaults and drop out on their own; a player's page never reads them. The water lock is a core rule (`lockWater`) rather than a tuning value because it still draws the seed's number for every bottle: unlocking resumes the seed's sequence and a locked run is the same run with other water, and Copy stays the pure tuning. Playwright's second web server (port 5197, `NODE_ENV=production`) lets e2e tests check the production flags without a build. |
| D25 | The mouse push is a grab in core (`Grab` for the samples, `MouseControl` as `sim.mouse` for the rules: `grab` / `drag` / `release` / `cancel`); the scene only forwards pointer events with their `timeStamp`. While grabbed the power bar is `pushPower` of the drag so far, starting at 0 at the press, and `Simulation.step()` counts steps with no event (`Grab.idle`) so a pointer that stops makes the bar fade. A release throws through `throwBottle(power, 'mouse')` if the push reaches `pushMinPower` (1), keeps that power on the bar, and otherwise throws nothing and puts the bar back to what it showed before the grab. A blur, a keyboard throw (Space during a drag) or a `placeBottle` ends the grab; the cursor is `grab` over a grabbable bottle and `grabbing` while dragging | The design makes mouse and keyboard the same power value, so everything after the push is `throwBottle` and a unit test checks that the same power, water and seed give the same flight step by step. The release counts the pointer as stopped since its last sample, so a pointer that rests for 150 ms throws nothing, and the bar shows that before the release rather than lying about it. A position outside the canvas can't be trusted (Phaser reports no moves there, so it would look like a teleport and a full-power flick). Giving the bar back on a dropped grab lets a click on the bottle leave the keyboard's setting alone. | D26 | A round is `throwsPerRound` (10) throws, kept by a `Round` the Simulation owns: `score`, `landings` and `streak` belong to the round, and `Simulation.restartRound()` resets them and puts a new bottle in the hand from any phase. | D29 | Sound reacts to events the simulation queues (`SimEvents`, drained by `Simulation.drainEvents()` once per frame by the Game scene), never to the simulation's state. ### Core state

```ts
type Phase = 'aiming' | 'flying' | 'result' | 'roundOver';
interface SimSnapshot {
  tick: number; seed: number; phase: Phase;
  power: number; // the power bar, 0–100 (the live push while dragging)
  dragging: boolean; // the mouse holds the bottle
  bottle: BodySnapshot & { water: number; waterOffset?: number }; // water: filled fraction 0–1
  lastThrow: { power: number; water: number; source: 'keyboard' | 'mouse' } | null;
  outcome: { result: 'success' | 'fail';
             reason: 'upright' | 'noFlip' | 'side' | 'cap' | 'offTable' | 'offScreen' | 'timeout';
             rotation: number; turns: number; // rotation: radians since release
             points: number } | null; // turns for a success, 0 for a fail
  resultSteps: number | null; // steps since the outcome; null outside the result phase
  score: number; // this round's points
  throws: number; // every bottle released by this simulation; never reset
  throwNumber: number; throwsPerRound: number; // "Throw 3 / 10": the round's own counter
  landings: number; streak: number; // this round's upright landings; consecutive ones
}
```

Flow: `aiming` → throw → `flying` → outcome → `result` → delay or `skip()` → `aiming`, or `roundOver` after throw 10. The simulation also queues events (`throw`, `impact` with speed, `outcome`) that the scene drains each frame for sound and effects.

### Key decisions

| # | Decision | Why |
| --- | --- | --- |
| P1 | Power is one number, 0–100; `throwBottle(power, source)` is the only way to throw | the design makes both inputs identical to the physics |
| P2 | The throw is an impulse that mass and inertia divide | heavier bottles get less speed and spin without special cases |
| P3 | Water is mass filling the bottle from the base to its level, solid until M6 | the drawn level and the physics agree |
| P4 | Outcomes are judged from physics state; nothing moves the bottle after release | the design says physics decides |
| P5 | Delays, hold times, timeouts and replay length count fixed steps in core | deterministic, and tests drive them with `step()` |
| P6 | Tuning is a plain object the Simulation accepts as overrides | the tuning panel and tests change the feel without code edits |
| P7 | Flip windows are measured by headless power sweeps and locked by unit tests | calibration can't silently regress |
| P8 | Screens and game pause live in `src/game`; pausing just stops stepping | core has no clock to pause |
| P9 | Sound and effects react to simulation events | core stays free of audio and Phaser |
| P10 | Saves use one versioned localStorage key; the rules (`updateBest`) live in core | storage is a browser API; the rules stay testable |
| P11 | Sloshing is a second body on a prismatic joint along the bottle's axis, behind a switch until recalibrated | the simplest moving mass that changes the flip |
